Stage 02 — the equals/hashCode contract, three outcomes
=======================================================

ROADMAP stage 2 asks for a hashCode built from only some of the fields, put
into a HashMap, and the entry then failing to come back. It does not fail.
This file records what each of the three key types actually does.

  1. hashCode from one of two fields, equals from both
     -> the entry IS retrieved. Equal objects still hash equally, so the
        contract holds. Two keys differing only in the ignored field share a
        bucket and are separated by equals. Cost: collisions, not entries.

  2. equals overridden, hashCode NOT overridden
     -> map.get(equalKey) returns null. Object.hashCode is identity-based, so
        the lookup picks the wrong bucket and never reaches equals.
        The value is still in the map: containsValue finds it.

  3. a mutable field inside hashCode, mutated after put
     -> map.get(theSameObject) returns null, and so does a lookup with a fresh
        key carrying the original value. The entry is stranded in the bucket
        its old hash chose. Map size is still 1 and containsValue finds it.

The compiler gate on case 2
---------------------------

CORRECTION. An earlier version of this file, and the commit message that
introduced it, claimed javac does not warn about case 2 under -Xlint:all
-Werror. That was wrong, and it was wrong because it was measured on an
incremental build that did not recompile the file. On a clean build javac
does catch it, and the build fails:

[INFO] BUILD FAILURE
[ERROR] /home/ubuntu/jerome/java-hands-on/domain/src/test/java/com/jerome/slledger/domain/identity/IdentityContractTest.java: warnings found and -Werror specified

So case 2 cannot be reproduced on this build without opting out by name. The
test class carries @SuppressWarnings("overrides") with a comment saying why.
The suppression is itself the finding: on this build, the most common way an
identity type is wrong is a build failure rather than a code review.

Cases 1 and 3 draw no warning. javac has nothing to say about a hashCode that
uses fewer fields than equals, nor about a mutable field inside hashCode --
the second of which is the one that loses entries silently in production.
