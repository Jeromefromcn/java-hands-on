Reading it:
- Offset page 0 already costs 36 ms, against 6 ms for the first keyset slice.
  The difference at depth 0 is the count(*) every offset response carries:
  a parallel sequential scan of all 500,000 rows, 37.8 ms on its own.
- The offset query itself walks the primary-key index from the start and
  discards 499,980 rows (actual rows=500000 on the Index Scan) to return 20:
  142 ms and 8,585 buffers. The keyset query seeks to the cursor
  (Index Cond: id > 'LP-499980') and reads 4 buffers.
- The rows returned were asserted equal both ways at every depth.

Correctness under insert (PaginationConsistencyIT, regular suite): with
LP-0005 inserted between two offset requests, page 1 starts with LP-0100,
which already ended page 0. The keyset walk returned each of the 30 original
rows exactly once.
