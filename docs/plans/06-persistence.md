# Stage 06 — Persistence · Implementation Plan

Spec: [`docs/specs/06-persistence.md`](../specs/06-persistence.md)

One section per commit, in order. Implement a section, tick its checkbox in
the same commit, then stop for review. `./mvnw clean verify` at the
repository root after every section (stage 5's record explains the `clean`).

## Ground rules for every section

- Packages:
  - `com.jerome.slledger.application.<usecase>`;
  - `com.jerome.slledger.adapter.persistence.<area>`;
  - test support in `com.jerome.slledger.adapter.persistence.testing`.

  `ArchitectureIT` matches on `adapter.persistence..` and `adapter.web..`,
  so these names are load-bearing.
- No `<version>` in a child POM. Every artifact comes from the
  `spring-boot-dependencies` 4.1.1 BOM, which supplies Hibernate 7.4.5,
  Flyway 12.4.0, HikariCP 7.0.2, PgJDBC 42.7.13 and Testcontainers 2.0.5.
- `@Transactional` appears only in `application`. ArchUnit rule 3 now
  governs real classes, so the adapter guards its transaction requirement
  in code (section 4) instead of by annotation.
- Tests that need Docker end in `IT` and run under failsafe. Pure unit
  tests end in `Test`.
- Every reproduced failure asserts its exception type, root cause or
  SQLState, never `Exception.class`. A test asserting wrong behaviour is
  named `reproduces<Failure>` and carries
  `// See docs/decisions/06-persistence.md`.
- Concurrency is sequenced with `CountDownLatch` / `CyclicBarrier`, never
  `Thread.sleep`. Every test that can block carries `@Timeout(30)` on top
  of its own `connectionTimeout` / `lock_timeout`.
- SQL is counted with Hibernate `Statistics`
  (`hibernate.generate_statistics=true` in test contexts only), not by
  reading logs.
- Evidence is written by tests to `<module>/target/evidence/06-*.txt` and
  copied by hand to `docs/evidence/`. A test never writes into `docs/`.
- Test data is synthetic: counterparties `CP-001…`, ISINs with valid check
  digits generated by the fixture, never a real issuer.

## Deviations from the spec, decided while planning

Each deviation is flagged in its section and carried to the decision record.

1. **The guard is an identity map, not `MANDATORY`.** `MANDATORY` only
   asserts that *some* transaction is active. The overwrite the spec names
   happens when the position is loaded in transaction 1 and saved in
   transaction 2, and transaction 2 *is* active, so `MANDATORY` passes and
   the overwrite still happens. The adapter instead binds a
   transaction-scoped identity map (`TransactionSynchronizationManager
   .bindResource`) of the aggregates it loaded. `add` of an existing
   position whose instance is not in the current transaction's map is
   refused. That also covers the no-transaction case. It is enforced in
   code, which also keeps rule 3 intact.
2. **`LoanPositionRepository` gets a third method,
   `activeOf(CounterpartyId)`.** The open use case's credit check needs the
   counterparty's positions. `domain`'s `LoanPositions
   .exposureByCounterparty` then computes exposure, so the currency rule
   stays in `domain`. The alternative was a SQL `sum()` in an application
   port, which would add up collateral across currencies unless the query
   remembered not to.
3. **A duplicate idempotency key raises `DuplicateRequestException`.**
   Returning the original result instead is stage 7's `Idempotency-Key`
   exercise.
4. **`ApplicationScanTest` and `ConfigurationPrecedenceTest` become
   `…IT`.** Once their `DataSourceAutoConfiguration` exclusion is removed,
   they need Docker, and Docker-backed tests run under failsafe.
5. **One container, many databases.** Stage 5's demos drop and recreate
   `loan_position`, and Flyway-managed tests need Flyway's `loan_position`.
   In one database the two would corrupt each other. `SharedPostgres` gains
   `freshDatabase()`, and each Flyway-managed context gets its own database
   (`CREATE DATABASE`, milliseconds). Stage 5's demos keep one shared
   `tx_demo` database with Flyway and JPA switched off.

## Review focus

These are failure modes the spec implies but no exercise is *about*. Each is
pinned by a test in the section named.

1. **A position loaded in one transaction and saved in another.** It is
   refused, not silently written (section 4).
2. **Money read back from a row written by something other than this code,
   with more precision than its currency.** It is refused on every money
   column, not only `accrual_entry` (section 3).
3. **A row whose `status` disagrees with its quantities**, for example
   `CLOSED` with 10 outstanding. `restore` refuses it, and so does the
   repository reading it (sections 2 and 3).
4. **An open request with a key already used by a return, or the reverse.**
   The unique constraint spans both directions and is rejected either way
   (section 5).
5. **Exposure across currencies.** A counterparty with a USD position
   opening an HKD one gets `CurrencyMismatchException` from `domain`, not a
   summed number (section 5).

// domain.loan
public static LoanPosition restore(

    Money collateral, AccrualRule accrualRule);

public interface LoanPositionRepository {

- `CLOSED` with `outstanding != 0`.

`LoanPositionTest` gains `restore` tests:

- each refusal above (Review focus 3);
- a restored `PARTIALLY_RETURNED` position accepts a return and closes;
- equality with an `open`ed position of the same id.

  race is still stage 8's. A row updated by two transactions is stage 6's

## [x] 3 · V1 schema, entities, mappers, and money at every column

**`db/migration/V1__ledger_tables.sql`**

| Table | Columns | Constraints |
|---|---|---|
| `counterparty` | `id text`, `name text`, `credit_limit_amount numeric(22,6)`, `credit_limit_currency char(3)` | primary key `id` |
| `security` | `isin char(12)`, `name`, `currency char(3)`, `market_price_amount numeric(22,6)`, `market_price_currency char(3)` | primary key `isin` |
| `loan_position` | `id text`, `counterparty_id`, `isin`, `original_quantity bigint`, `outstanding_quantity bigint`, `status text`, `collateral_amount numeric(22,6)`, `collateral_currency char(3)`, `rule_type text`, `flat_rate numeric(12,8)` | primary key `id`; foreign keys to `counterparty` and `security` |
| `loan_trade` | `id bigserial`, `idempotency_key text not null`, `position_id`, `counterparty_id`, `isin`, `direction text`, `quantity bigint`, `unit_price_amount`, `unit_price_currency`, `trade_date date`, `settlement_date date` | primary key `id`; **unique `idempotency_key`** |

Every column is `not null`.

- The `rate` scale, `numeric(12,8)`, must hold every `Rate` that
  `AccrualRuleProperties` allows. That is checked, not assumed, against
  `Rate`'s own validation.
- `numeric(22,6)` leaves 16 integer digits. The decision record states the
  headroom against the largest notional the fixtures use.

**`adapter.persistence`**
- One entity per table: `CounterpartyEntity`, `SecurityEntity`,
  `LoanPositionEntity` (with `@OneToMany(mappedBy…, fetch = LAZY)
  List<AccrualEntryEntity> entries`, for exercises 2 and 3), `LoanTradeEntity`
  and `AccrualEntryEntity`.
  - Each has a protected no-arg constructor.
  - No entity is exposed outside the adapter.
- `MoneyColumns.read(BigDecimal stored, String currencyCode) → Money`:
  - trims the `char(3)`;
  - builds the `Money`;
  - throws `ArithmeticException` if `stored.compareTo(money.amount()) != 0`.

  This is stage 5's rule, now in one place that every mapper uses.
- `AccrualRuleColumns`:
  - `FlatRate` ↔ (`"FLAT"`, rate).
  - Any other rule throws `UnsupportedAccrualRuleException`, an adapter
    exception naming the rule's class.
- `LoanPositionMapper`, `LoanTradeMapper`, `CounterpartyMapper`,
  `AccrualEntryMapper`. Positions are rebuilt only through `restore`.
- `PersistenceConfiguration` (`@Configuration`, `@EntityScan`,
  `@EnableJpaRepositories` on `adapter.persistence`). It is imported by
  `bootstrap` later, and by the test application now.

**Test support** (`testing`)
- `PersistenceTestApplication`: `@SpringBootConfiguration`,
  `@EnableAutoConfiguration`, `@Import(PersistenceConfiguration.class)`.
- `LedgerDb.start(String[] extraProperties, Class<?>... beans)`:
  - Uses `freshDatabase()`.
  - Sets `spring.jpa.hibernate.ddl-auto=validate`,
    `spring.jpa.open-in-view=false` and
    `hibernate.generate_statistics=true`.
- `LedgerFixtures` (`JdbcClient`): `counterparty(…)`, `security(…)`,
  `position(…)`, `entries(positionId, from, days, fee)`.

**`MoneyColumnsRoundTripIT`**
- Parameterised over `HKD` / `JPY` / `BHD`, for every money column:
  credit limit, market price, collateral, unit price and fee.
  - write through the mapper, read back, then assert equality and scale;
  - insert a raw row with one digit too many and assert `ArithmeticException`
    on read (Review focus 2).
- `restore`'s refusal is reached from a raw row: a `CLOSED` row with 10
  outstanding produces `IllegalArgumentException` on read.
- A `FloatingRate` position produces `UnsupportedAccrualRuleException` on
  write.
- The context starting at all is the `ddl-auto=validate` check.

**Acceptance**
- The ITs above pass, and Hibernate validation passes against V1.
- `./mvnw clean verify` is green.

**Found while implementing**
- **`flat_rate` is unconstrained `numeric`, not `numeric(12,8)`.** `Rate` is
  deliberately not normalised, and its record equality compares `BigDecimal`
  scale. A fixed-scale column pads `0.0400` to `0.04000000`, so the rate reads
  back as a different `Rate`, and it would round anything past 8 places.
  Measured by mutation in `docs/evidence/06-money-columns.txt`.
- **`LoanPosition`'s `collateral()`, `counterparty()`, `security()` and
  `accrualRule()` are now public.** The mapper sits outside `domain.loan`
  and has to read every field to store it. The fields are final and
  immutable, so reading them opens no path to a state change. The
  `LoanPositions` Javadoc that justified its package by those getters being
  package-private was updated.
- **`accrual_entry` uses a primary key `(position_id, business_date)`, not a
  unique constraint.** JPA needs an id, and the primary key is the same rule
  and the same index. Exercise 8's "no index" run drops the primary key.
- **`LedgerFixtures` is deferred** to the first section that inserts rows the
  mappers cannot write (section 9). This section writes everything through
  the mappers.

## [x] 4 · V2 `version`, the optimistic repository, and its guard

- **`V2__loan_position_version.sql`**:
  `ALTER TABLE loan_position ADD COLUMN version bigint NOT NULL DEFAULT 0`.
  `LoanPositionEntity` gains `@Version long version`.
- **`OptimisticLoanPositionRepository implements LoanPositionRepository`**:
  - `find`: `jpa.findById` → `LoanPositionMapper.toDomain`, then
    registers `(domainInstance → entity)` in the transaction-scoped
    identity map.
  - `add`:
    - Instance in the map: copy `outstandingQuantity` and `status` onto the
      managed entity. The flush does the rest.
    - Instance not in the map and the id already exists: throw
      `PositionNotLoadedInThisTransactionException` (deviation 1).
    - New id: `persist`.
    - No transaction active: `IllegalTransactionStateException`.
  - `activeOf`: a derived query on `counterpartyId` with status not
    `CLOSED`. Each result is registered in the map too.
- **`UnitOfWorkPositions`**: the identity map.
  - An `IdentityHashMap` bound with
    `TransactionSynchronizationManager.bindResource`.
  - Unbound in `afterCompletion`, so no pooled thread carries it into the
    next transaction.

**`LoanPositionRepositoryContract`** is an abstract JUnit class. Section 12
reuses it for the pessimistic adapter.
- `find` after `add` returns an equal position;
- a return written back is visible to a fresh transaction;
- `activeOf` excludes `CLOSED`;
- `add` outside a transaction is refused;
- `add` of an instance loaded in an earlier, committed transaction is
  refused (Review focus 1).

**`OptimisticLoanPositionRepositoryIT extends LoanPositionRepositoryContract`**
also covers:
- after one write-back the version goes 0 → 1;
- **`reproducesSilentOverwriteAcrossTransactions`**:
  - `NaiveLoanPositionRepository` is a test-only adapter that maps into a
    fresh entity on every save (the "map every time" shape).
  - T1 loads P1 (100). T2 loads, returns 30, and commits. T3 saves T1's
    stale instance after returning 10.
  - Result: outstanding is **90**, T2's return has vanished, and no
    exception is raised.
  - The same sequence through the real adapter is refused at T3.

**Acceptance**
- The contract passes for the optimistic adapter.
- The reproduction shows 90.
- `./mvnw clean verify` is green.

**Found while implementing**
- **`find` and `activeOf` are refused outside a transaction too, not only
  `add`.** An instance loaded outside a transaction can never be written
  back, because no transaction's map holds it. Refusing at `find` reports
  the mistake where it is made, not at a later `add`. Read-only callers use
  the application's projection port, which needs no aggregate.
- **The contract has two tests beyond the list above.**
  - `aChangeNeverPassedBackToAddIsNotStored` pins the `add` Javadoc
    corrected in section 2.
  - `aNewInstanceWithAnIdAlreadyStoredIsRefusedNotMerged` pins the "id
    already exists" branch for an instance that was never loaded at all.

  Both are behaviour the pessimistic adapter must share.

## [x] 5 · Use cases in `application`, wired in `bootstrap`

**`application.position`**

```java
public record OpenPositionCommand(IdempotencyKey key, CounterpartyId counterparty, Isin security,
    long quantity, Money collateral, AccrualRule rule, LocalDate tradeDate) {}
public record ReturnCommand(IdempotencyKey key, LoanPositionId position, long quantity,
    LocalDate tradeDate) {}

public class OpenPosition {            // @Transactional on open()
  public LoanPositionId open(OpenPositionCommand c);
}
public class ReturnPositionOnce {      // @Transactional on apply()
  public void apply(ReturnCommand c);
}
public class ReturnPosition {          // NOT transactional: the retry loop
  public ReturnPosition(ReturnPositionOnce once, int maxAttempts);
  public void apply(ReturnCommand c);  // retries on OptimisticLockingFailureException
}
```

**Ports in `application`**
- `CounterpartyDirectory.find(CounterpartyId) → Optional<Counterparty>`
- `SecurityDirectory.find(Isin) → Optional<Security>`
- `TradeLedger.book(LoanTrade)`. A duplicate key raises
  `DuplicateRequestException`, translated from the unique violation
  (deviation 3).
- `PositionListQuery.page(int page, int size) → PositionPage` (records of
  `PositionRow`).

**Behaviour of `OpenPosition.open`**
1. Load the counterparty.
2. `repository.activeOf` → `LoanPositions.exposureByCounterparty(…,
   collateral.currency())` → `creditLimit.checkCanAbsorb`.
3. `LoanPosition.open` with a UUID id.
4. `add`.
5. Book a `BORROW` trade at the security's market price, settling on
   `SettlementDates.settlementDate(tradeDate, new HongKongHolidays())`.

`ReturnPositionOnce.apply` is find → `returnQuantity` → `add` → book `RETURN`.

**Adapters**
- `JpaCounterpartyDirectory`, `JpaSecurityDirectory` and `JpaTradeLedger`.
  `JpaTradeLedger` flushes inside `book`, so the unique violation surfaces
  in the use case, not at commit.
- `JpaPositionListQuery`: a constructor-expression JPQL projection, ordered
  by `id`.

**`bootstrap`**
- `LedgerConfiguration` is a `@Configuration` with `@Import
  (PersistenceConfiguration.class)`, plus `@Bean`s for the four use cases.
  `ledger.return.max-attempts` defaults to 3.
- `application.yml` gains:
  - `spring.jpa.open-in-view: false`;
  - `spring.jpa.hibernate.ddl-auto: validate`;
  - `spring.jpa.properties.hibernate.cache.use_second_level_cache: false`.
- `ApplicationScanTest` → `ApplicationScanIT`, and
  `ConfigurationPrecedenceTest` → `ConfigurationPrecedenceIT`
  (deviation 4). Both use `freshDatabase()`, their
  `DataSourceAutoConfiguration` exclusion is removed, and their assertions
  are unchanged.

**`bootstrap` `PositionUseCasesIT`**
- open, then list shows it;
- open over the credit limit: `InsufficientCreditException` and nothing
  persisted;
- the same key twice: `DuplicateRequestException` and one position;
- a return reusing an open's key, and the reverse: `DuplicateRequestException`
  (Review focus 4);
- a USD position plus an HKD open: `CurrencyMismatchException`
  (Review focus 5);
- a partial then a full return closes the position, with 3 trades.

**Acceptance**
- The ITs pass.
- `ArchitectureIT` passes and now has classes in `application` and
  `adapter-persistence`. Rule 1 and rule 2 are no longer vacuous, and the
  Javadoc saying they are is updated.
- `./mvnw clean verify` is green.

**Found while implementing**
- **Adapters are registered by component scan, not by `@Bean` methods.**
  They are `@Repository` / `@Component` beans picked up by
  `PersistenceConfiguration`'s `@ComponentScan`. They depend on Spring Data
  interfaces that are package-private to their own package, which a factory
  method in the configuration's package cannot name. Section 4's tests now
  get the optimistic adapter from the scan.
- **`PositionNotLoadedInThisTransactionException` extends
  `RuntimeException`, not `IllegalStateException`.** This was observed, not
  predicted: once the adapter became a `@Repository`, Spring's persistence
  exception translation turned it into `InvalidDataAccessApiUsageException`
  (`EntityManagerFactoryUtils.convertJpaAccessExceptionIfPossible`), and
  three section 4 tests failed on the type.
- **Rules 1 and 3 are no longer vacuous; rule 2 still is.** `adapter-web`
  stays empty until stage 7. The plan's "rule 1 and rule 2" was wrong.
- **The two renamed full-application tests pass the datasource as
  command-line arguments.** `SpringApplicationBuilder.properties` sets
  default properties, the lowest precedence, and section 6 puts a
  datasource into `application-local.yml`, which would override them.
- **Additions the plan implied but did not name.**
  - `ListPositions`, the listing use case, is `@Transactional(readOnly =
    true)`. Its Javadoc states that read-only does not make the page and the
    count one snapshot.
  - `UnknownReferenceException` covers an unknown counterparty, security or
    position.
  - `ReturnPosition` rethrows the last `OptimisticLockingFailureException`
    when attempts run out.
- **Duplicate detection matches the constraint name**
  (`loan_trade_idempotency_key_key`) through Hibernate's
  `ConstraintViolationException`. When the name was mutated, the three
  duplicate tests failed.

## [x] 7 · Exercise 1 — Flyway: breaking change and expand/contract

These migrations are test-only, under
`adapter-persistence/src/test/resources/db/lab/bluegreen/`. They are
numbered from V1000 so they can never collide with production.

- `breaking/V1000__idempotency_key_to_uuid.sql`:
  `ALTER COLUMN idempotency_key TYPE uuid USING idempotency_key::uuid`.
- `expand/V1001__add_idempotency_uuid.sql`: a nullable `idempotency_uuid
  uuid` plus a unique index.
- `expand/V1002__dual_write_and_backfill.sql`:
  - A trigger fills `idempotency_uuid` on insert when an old writer leaves
    it null.
  - The backfill sets it for existing rows.
  - For both: a UUID-shaped key is cast, and any other key is mapped
    deterministically with `md5(key)::uuid`.
- `contract/V1003__drop_text_key.sql`: drop the trigger and the text
  column, rename `idempotency_uuid`, set it `not null`.

**`BlueGreenMigrationIT`**
- Each case runs Flyway with `locations` of
  `classpath:db/migration,classpath:db/lab/bluegreen/<step>` on a fresh
  database.
- Two writers are defined:
  - "old app" is a `PreparedStatement` that inserts a `loan_trade` with
    `setString` on `idempotency_key`, using a key like `"req-42"`;
  - "new app" writes a UUID key through the new column.
- **`reproducesBlueGreenBreakageOnColumnTypeChange`** has two parts:
  - Migrating a database that holds an old `"req-42"` row fails at the
    `USING` cast, with SQLState `22P02`.
  - On an empty database the migration succeeds, and the old writer then
    fails. The prediction is SQLState `42804` (`uuid` vs
    `character varying`). The test records what was actually observed.
- `expandContractKeepsBothVersionsWorking`:
  - After V1001 and after V1002, both writers succeed and no row has a
    null `idempotency_uuid` after V1002.
  - After V1003, only the new writer is expected to succeed. The old
    writer's failure is asserted and captioned "old version retired before
    contract".

Evidence: `docs/evidence/06-blue-green.txt`.

**Acceptance**
- Both tests pass.
- `db/migration` still holds only production files.
- `./mvnw clean verify` is green.

**Found while implementing**
- **V1003 does not rename `idempotency_uuid` back to `idempotency_key`.** The
  version deployed during expand writes `idempotency_uuid`; a rename in
  contract would break that version exactly as V1000 broke the old one, and
  would need an expand/contract of its own. The column keeps its new name.
- **The old writer fails on the bind type, not on the key's shape.** A valid
  UUID string sent through `setString` fails with `42804` as well, so no
  choice of keys by the old version would have saved it.
- **The deterministic mapping is asserted directly**: after V1002, no row's
  `idempotency_uuid` differs from `idempotency_uuid_of(idempotency_key)`. A
  resubmitted key colliding would not prove it, because the text column's

## [x] 9 · Exercise 2 — N+1 and the pagination trap

The fixture is 100 positions with 5 entries each.

**`NPlusOneIT`**
- **`reproducesNPlusOne`**: `findAll()`, then touching each `entries`,
  gives **101** prepared statements.
- `joinFetchLoadsInOneStatement`: `select distinct p from … join fetch
  p.entries` gives 1 statement, 100 positions and 500 entries.
- `entityGraphLoadsInOneStatement`: `@EntityGraph(attributePaths =
  "entries")` gives 1 statement, with the same counts.
- `batchSizeLoadsInFewStatements`: `@BatchSize(size = 25)` on `entries`.
  The prediction is 1 + 4 = 5 statements, and the test asserts the
  measured count with its reasoning. Entries are complete.
- **`reproducesInMemoryPaginationWithJoinFetch`**:
  - `join fetch` combined with `setMaxResults(10)`.
  - Hibernate logs `HHH90003004`, captured with a log appender.
  - The generated SQL has no `limit`, taken from the statement inspector.
  - It returns 10 positions after reading all 500 rows.
- The same query with
  `hibernate.query.fail_on_pagination_over_collection_fetch=true` throws.
  The exception type is confirmed against Hibernate 7.4 in this section.
- `twoQueryPaginationIsCorrect`: page the ids first, then fetch by ids. It
  asserts `limit` in the SQL and 2 statements.

Evidence: `docs/evidence/06-n-plus-one.txt`, with the count per variant
and the two SQL texts.

**Acceptance**
- The tests pass.
- `./mvnw clean verify` is green.

**Found while implementing**
- **The pagination trap, as planned, does not reproduce on Hibernate 7.4.5.**
  `join fetch` (with or without `distinct`, inner or left) and the entity
  graph, each with `setMaxResults(10)`, are rewritten: the page is taken over
  positions in a subquery (`from (select … fetch first ? rows only)`), then
  joined to entries. 10 positions, 60 entities, no warning.
- **It still fires when the order refers to the fetched collection**
  (`order by p.id, e.businessDate`): no `limit`, 600 entities hydrated for 10
  positions, `HHH90003004`. That is `reproducesInMemoryPaginationWithJoinFetch`
  now. The strict setting throws `org.hibernate.HibernateException`.
- **A worse failure, not predicted: a page silently ignored.** The rewrite is
  decided when a query string is first interpreted and cached per session
  factory. If the same `join fetch` string ran once without a page, every later
  `setMaxResults(10)` on it returns all 100 positions, with no warning.
  `hibernate.query.plan_cache_enabled=false` restores 10. Pinned as
  `reproducesPageIgnoredAfterTheSameQueryRanUnpaged`. The reverse order is
  correct. No production query is affected: `JpaPositionListQuery` is a
  projection with no fetch.
- **The entity graph is built with the JPA API, and batch fetching is
  `hibernate.default_batch_fetch_size=25` in its own context**, not
  `@EntityGraph` / `@BatchSize` on production types. Either annotation on
  `LoanPositionEntity` or its repository would change what the N+1
  reproduction measures. The mechanism is the same.
